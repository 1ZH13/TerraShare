Introducción y contexto

TerraShare es una plataforma de comercio electrónico para el alquiler de terrenos en Panamá. Conecta a dueños que publican parcelas con arrendatarios que las solicitan, cubriendo el ciclo completo: catálogo con filtros, solicitud de alquiler, contrato, pago (Stripe), chat interno y panel de administración.

El MVP está construido como un monorepo con tres paquetes: apps/backend-api (Bun + Hono + MongoDB/Mongoose), apps/web (React + Vite) y packages/shared (tipos y contratos compartidos).

Este documento lista las funcionalidades en formato de historias de usuario divididas en: (1) lo que ya se implementó, (2) lo que falta para considerar el proyecto production-ready, y (3) las funcionalidades a exponer mediante un servidor MCP (Model Context Protocol) bajo autenticación, importable desde Claude Code o Codex, que alimentará el próximo proyecto.

Sección 1 — Inventario actual (implementado)

Funcionalidades que ya existen en el MVP, derivadas del código del backend (rutas Hono) y del frontend (13 páginas React).

Autenticación, perfiles y roles

HU-01Registro e inicio de sesión

Como visitante, quiero registrarme e iniciar sesión, para acceder a las funciones autenticadas de la plataforma.

  • El registro/login se realiza vía Clerk con email y contraseña.
  • Tras autenticarse, el usuario recibe un token válido para llamar a la API.
  • Las rutas protegidas rechazan peticiones sin token con 401.
HU-02Consultar mi perfil

Como usuario autenticado, quiero consultar mi perfil con GET /auth/me, para ver mis datos y mi rol.

  • Devuelve id, email, nombre, rol (user/admin) y estado.
  • Si el usuario está bloqueado (inactive), se deniega el acceso con 403.
HU-03Control de acceso por rol (RBAC)

Como administrador, quiero que ciertas rutas exijan rol admin, para proteger operaciones sensibles.

  • El middleware requireAdmin bloquea a usuarios sin rol admin con 403.
  • Existe un endpoint de verificación GET /auth/admin/ping.
HU-04Bypass de autenticación en desarrollo

Como desarrollador, quiero un bypass de auth en entorno dev (cabecera x-dev-user-id), para probar flujos sin depender de Clerk.

  • Solo se activa cuando ALLOW_DEV_AUTH_BYPASS=true.
  • Permite simular usuarios y roles mediante cabeceras x-dev-user-id / x-dev-role.

Catálogo y gestión de terrenos

HU-05Explorar el catálogo con paginación

Como visitante, quiero ver el catálogo de terrenos paginado, para explorar la oferta disponible.

  • GET /lands devuelve solo terrenos en estado active.
  • Soporta page y pageSize con metadatos de paginación (total, páginas).
HU-06Filtrar terrenos

Como visitante, quiero filtrar terrenos por uso, provincia, distrito, precio y disponibilidad, para encontrar lo que necesito.

  • Filtros por use, province, district, priceMin/priceMax y rango de fechas.
  • Los filtros se combinan (AND) y respetan la paginación.
HU-07Ordenar resultados

Como visitante, quiero ordenar el catálogo por fecha, precio o área, para priorizar lo que más me interesa.

  • Soporta sort=createdAt|price|area y order=asc|desc.
  • Un valor de orden inválido devuelve 400 con mensaje claro.
HU-08Ver detalle de un terreno

Como visitante, quiero ver el detalle de un terreno, para conocer ubicación, área, usos permitidos y precio.

  • GET /lands/:id devuelve la ficha completa.
  • Un terreno inexistente o inactivo devuelve 404.
HU-09Publicar un terreno

Como dueño, quiero crear un terreno, para ponerlo en alquiler.

  • POST /lands valida campos requeridos (título, área, ubicación, precio, usos).
  • El terreno se crea en estado draft y queda asociado al dueño autenticado.
  • Se registra un evento de auditoría land/created.
HU-10Editar mi terreno

Como dueño, quiero editar mi terreno, para mantener su información actualizada.

  • Solo el dueño o un admin pueden editar (PATCH /lands/:id), si no 403.
  • El id y el dueño no se pueden alterar; se actualiza updatedAt.
HU-11Cambiar el estado del terreno

Como dueño, quiero cambiar el estado de mi terreno (draft/active/inactive), para controlar su visibilidad en el catálogo.

  • PATCH /lands/:id/status acepta solo estados válidos.
  • Solo terrenos active aparecen en el catálogo público.
HU-12Eliminar mi terreno

Como dueño, quiero eliminar un terreno, para retirarlo de la plataforma.

  • DELETE /lands/:id solo lo permite el dueño o admin.
  • Se registra evento de auditoría land/deleted.
HU-13Ver mis terrenos

Como dueño, quiero listar mis terrenos (GET /lands/me), para gestionarlos desde un solo lugar.

  • Devuelve únicamente los terrenos cuyo ownerId es el del usuario.
  • La página «Mis Terrenos» del frontend los muestra con sus estados.

Solicitudes de alquiler

HU-14Crear una solicitud de alquiler

Como arrendatario, quiero crear una solicitud de alquiler sobre un terreno, para reservar su uso por un período.

  • POST /rental-requests valida período (inicio < fin) y uso previsto.
  • Un dueño no puede solicitar su propio terreno (422).
HU-15Listar mis solicitudes

Como usuario, quiero listar mis solicitudes de alquiler, para hacer seguimiento de su estado.

  • El arrendatario ve sus solicitudes; el dueño ve las de sus terrenos.
  • Se puede filtrar por estado.
HU-16Ver detalle de una solicitud

Como usuario, quiero ver el detalle de una solicitud, para conocer fechas, estado y terreno asociado.

  • GET /rental-requests/:id devuelve la solicitud y datos del terreno.
  • Solo las partes involucradas o un admin pueden verla.
HU-17Aprobar / rechazar solicitudes

Como dueño, quiero cambiar el estado de una solicitud (aprobar/rechazar/cancelar), para gestionar la demanda de mi terreno.

  • PATCH /rental-requests/:id/status aplica transiciones válidas de estado.
  • Solo el dueño del terreno o admin pueden cambiar el estado.
HU-18Evitar reservas solapadas

Como sistema, quiero impedir solicitudes aprobadas con fechas solapadas en el mismo terreno, para evitar la doble reserva.

  • Si existe una solicitud aprobada/pagada que se solapa, devuelve 409 CONFLICT.
  • La validación considera el rango [startDate, endDate].

Contratos y auditoría

HU-19Generar un contrato

Como dueño, quiero generar un contrato a partir de una solicitud, para formalizar el alquiler.

  • POST /contracts crea el contrato en estado draft con términos y fechas.
  • Queda vinculado a la solicitud, dueño y arrendatario.
HU-20Firmar un contrato

Como parte del contrato, quiero firmar el contrato, para dar mi consentimiento.

  • POST /contracts/:id/sign solo es válido si el contrato está en draft.
  • Al firmar pasa a active y registra signedAt + evento de auditoría.
HU-21Completar un contrato

Como dueño, quiero completar un contrato activo, para cerrar el ciclo de alquiler.

  • POST /contracts/:id/complete solo procede si está active.
  • Transición inválida devuelve INVALID_TRANSITION.
HU-22Consultar eventos de auditoría

Como administrador, quiero consultar la bitácora de auditoría, para rastrear acciones sobre entidades.

  • GET /audit-events permite filtrar por actor, entidad, acción e id.
  • Cada evento registra actor, rol, entidad, acción y fecha.

Pagos

HU-23Iniciar un pago (Stripe Checkout)

Como arrendatario, quiero iniciar el pago de una solicitud aprobada, para concretar el alquiler.

  • POST /payments/checkout-session crea una sesión de Stripe y devuelve checkoutUrl.
  • Solo se permite si la solicitud está approved/pending_payment.
HU-24Procesar webhooks de pago

Como sistema, quiero recibir webhooks de Stripe, para actualizar el estado del pago automáticamente.

  • POST /webhooks/stripe procesa checkout.session.completed.
  • Actualiza el pago a paid y refleja el cambio en la solicitud.
HU-25Ver mis pagos

Como usuario, quiero listar y ver el detalle de mis pagos, para conocer su estado.

  • GET /payments y GET /payments/:id muestran solo los pagos del usuario.
  • El frontend ofrece páginas de éxito y cancelación de pago.

Chat y contacto

HU-26Chat interno por terreno/solicitud

Como usuario, quiero un chat interno asociado a un terreno o solicitud, para coordinar con la otra parte.

  • GET/POST /chats lista y crea conversaciones entre participantes.
  • Solo los participantes pueden acceder a la conversación.
HU-27Enviar y leer mensajes

Como participante, quiero enviar y leer mensajes dentro de un chat, para comunicarme.

  • GET/POST /chats/:id/messages gestiona los mensajes ordenados por fecha.
  • Solo participantes del chat pueden publicar mensajes.
HU-28Contacto externo por WhatsApp

Como interesado, quiero un enlace de contacto externo (WhatsApp) con el dueño, para una comunicación más directa.

  • GET /chats/:id/external-contact entrega el contacto cuando está habilitado.
  • Se controla mediante WHATSAPP_CONTACT_ENABLED.

Administración, leads y analítica

HU-29Gestión de usuarios (admin)

Como administrador, quiero listar, ver y cambiar el estado de usuarios, para moderar la plataforma.

  • GET /admin/users, GET /admin/users/:id y PATCH /admin/users/:id/status.
  • Un admin no puede cambiar su propio estado.
HU-30Moderación de terrenos y panel (admin)

Como administrador, quiero moderar terrenos y ver un panel resumen, para supervisar la operación.

  • GET /admin/lands + PATCH /admin/lands/:id/status para moderar publicaciones.
  • GET /admin/summary y GET /admin/rental-requests alimentan el dashboard.
HU-31Captura de leads

Como visitante, quiero dejar mi correo desde la landing, para recibir información de la plataforma.

  • POST /leads registra el correo y su origen (landing/app-web/admin).
  • GET /leads permite a admin consultarlos.
HU-32Analítica e indicadores

Como dueño/administrador, quiero ver métricas de la plataforma, para tomar decisiones.

  • GET /analytics/overview, /analytics/lands, /analytics/requests.
  • GET /analytics/owner/:ownerId entrega métricas por dueño.
  • El catálogo incluye un mapa de Panamá (Leaflet) con provincias.

Sección 2 — Faltante / Production-Ready

30 historias nuevas necesarias para llevar el MVP a un estado production-ready: seguridad, pagos reales, observabilidad, manejo de errores, pruebas, CI/CD, roles, rate limiting, respaldos, accesibilidad e i18n.

Seguridad y autorización

HU-33Verificación de firma de webhooks

Como sistema, quiero verificar la firma de los webhooks de Stripe en producción, para evitar eventos falsificados.

  • Se valida Stripe-Signature con STRIPE_WEBHOOK_SECRET antes de procesar.
  • Eventos con firma inválida se rechazan con 400 y se registran.
HU-34Validación y sanitización de entrada

Como sistema, quiero validar y sanitizar toda entrada con esquemas (Zod), para prevenir datos inválidos e inyecciones.

  • Cada endpoint valida body/query con un esquema y devuelve errores estructurados.
  • Se rechazan campos no permitidos y tipos incorrectos.
HU-35Roles y permisos granulares

Como administrador, quiero permisos granulares por recurso (ownership consistente), para un control de acceso fino.

  • Matriz de permisos por rol y verificación de propiedad en cada acción.
  • Pruebas que cubran accesos no autorizados (403) en todos los recursos.
HU-36Gestión segura de secretos

Como equipo DevOps, quiero gestionar secretos fuera del repositorio (vault/variables seguras), para no exponer credenciales.

  • Ningún secreto vive en el código ni en el control de versiones.
  • Rotación de claves documentada y soportada por entorno.
HU-37Autenticación multifactor (MFA)

Como usuario, quiero habilitar 2FA/MFA, para proteger mejor mi cuenta.

  • Soporte de segundo factor (TOTP o email) en el login.
  • Configurable como obligatorio para cuentas admin.
HU-38Recuperación de contraseña

Como usuario, quiero recuperar mi contraseña de forma segura, para no perder el acceso.

  • Flujo de reset con token de un solo uso y expiración.
  • Notificación al correo y revocación de sesiones tras el cambio.
HU-39Cabeceras de seguridad y CORS estricto

Como sistema, quiero cabeceras de seguridad (HSTS, CSP) y CORS por entorno, para reducir la superficie de ataque.

  • CORS restringe orígenes según entorno (no * en producción).
  • Se aplican cabeceras de seguridad estándar a todas las respuestas.
HU-40Rate limiting por usuario/clave

Como sistema, quiero limitar la tasa por usuario y por clave de API (no solo por IP), para mitigar abuso de cuentas autenticadas.

  • Límites configurables por identidad y por tool de MCP.
  • Respuestas 429 con cabeceras Retry-After.

Pagos reales

HU-41Pagos reales y conciliación

Como negocio, quiero operar Stripe en modo real con conciliación, para procesar dinero efectivamente.

  • Claves live, manejo de moneda y comisiones.
  • Conciliación entre pagos, solicitudes y contratos.
HU-42Idempotencia en pagos

Como sistema, quiero claves de idempotencia en pagos y webhooks, para evitar cobros o actualizaciones duplicadas.

  • Cada operación de pago usa Idempotency-Key.
  • Webhooks duplicados no producen efectos repetidos.
HU-43Reembolsos y facturación

Como administrador, quiero gestionar reembolsos y emitir recibos, para cumplir con la operación comercial.

  • Endpoint de reembolso total/parcial con auditoría.
  • Generación de recibo/factura descargable para el usuario.

Observabilidad

HU-44Logs estructurados con correlación

Como equipo de operaciones, quiero logs estructurados (JSON) correlacionados por requestId, para depurar incidentes.

  • Cada log incluye nivel, timestamp, requestId, ruta y usuario.
  • Se envían a un agregador central (p. ej. Loki/ELK).
HU-45Métricas y dashboards

Como equipo, quiero métricas (Prometheus) y dashboards, para vigilar la salud del sistema.

  • Métricas de latencia, throughput y tasa de errores por endpoint.
  • Dashboard con SLOs visibles (Grafana).
HU-46Tracing distribuido

Como equipo, quiero trazas distribuidas (OpenTelemetry), para seguir una petición de extremo a extremo.

  • Spans desde la API hasta MongoDB y Stripe.
  • Trace-id propagado y visible en los logs.
HU-47Alertas y monitoreo

Como equipo de operaciones, quiero alertas automáticas, para reaccionar ante caídas o picos de error.

  • Alertas por error rate, latencia y disponibilidad.
  • Notificación a un canal (email/Slack) con runbook asociado.
HU-48Health/Readiness/Liveness probes

Como orquestador, quiero sondas de salud, readiness y liveness, para gestionar el ciclo de vida del servicio.

  • /health verifica dependencias (DB, Stripe).
  • Readiness separa "arrancando" de "listo para tráfico".

Manejo de errores y resiliencia

HU-49Manejo centralizado de errores

Como usuario, quiero mensajes de error claros y consistentes, para entender qué salió mal.

  • Catálogo de códigos de error y respuestas uniformes (ya parcialmente existente).
  • El frontend muestra estados de error y vacío amigables.
HU-50Reintentos y circuit breaker

Como sistema, quiero reintentos con backoff y circuit breaker hacia servicios externos, para tolerar fallos transitorios.

  • Reintentos idempotentes ante fallos de Stripe/DB.
  • El circuito se abre tras N fallos y se recupera automáticamente.

Pruebas, CI/CD y despliegue

HU-51Pruebas unitarias del backend

Como desarrollador, quiero cobertura de pruebas unitarias, para evitar regresiones.

  • Cobertura mínima acordada (p. ej. ≥70%) en lógica de negocio.
  • Las pruebas corren con MongoDB en memoria (sin DB externa).
HU-52Pruebas E2E de flujos críticos

Como equipo, quiero pruebas E2E (Playwright) de los flujos clave, para validar la experiencia completa.

  • Cubre login, publicar terreno, solicitar, contratar y pagar.
  • Se ejecutan en CI sobre un entorno efímero.
HU-53Pipeline de CI bloqueante

Como equipo, quiero un pipeline de CI (lint, typecheck, test) que bloquee merges, para mantener la calidad.

  • El merge a main requiere CI verde.
  • Typecheck del backend y build del web en 0 errores.
HU-54Despliegue continuo (CD)

Como equipo, quiero CD a staging y producción, para entregar cambios de forma segura y repetible.

  • Despliegues automatizados con estrategia de rollback.
  • Variables por entorno y promoción staging→prod controlada.
HU-55Migraciones de base de datos versionadas

Como equipo, quiero migraciones versionadas, para evolucionar el esquema sin pérdida de datos.

  • Migraciones reproducibles y reversibles.
  • Índices únicos (id, clerkUserId) creados de forma consistente.

Datos y operación

HU-56Respaldos automáticos y restauración

Como equipo de operaciones, quiero respaldos automáticos con restauración probada, para no perder datos.

  • Backups periódicos cifrados de MongoDB.
  • Restauración verificada al menos una vez por ciclo.
HU-57Privacidad y retención de datos

Como usuario, quiero control sobre mis datos personales, para ejercer mis derechos (Habeas Data/GDPR).

  • Exportación y borrado de datos a solicitud.
  • Política de retención y anonimización documentada.
HU-58Almacenamiento de imágenes de terrenos

Como dueño, quiero subir fotos de mi terreno a un almacenamiento (S3/CDN), para mostrarlo mejor.

  • Carga con validación de tipo/tamaño y URLs servidas por CDN.
  • Miniaturas optimizadas para el catálogo.
HU-59Búsqueda full-text y geoespacial

Como visitante, quiero buscar terrenos por texto y cercanía geográfica, para encontrar opciones relevantes.

  • Índice de texto sobre título/descripción.
  • Consulta por radio usando coordenadas (lat/lng).

Experiencia, inclusión y entrega

HU-60Notificaciones reales (email/push)

Como usuario, quiero recibir notificaciones por email/push de eventos clave, para enterarme a tiempo.

  • Entrega real ante aprobación de solicitud, pago y mensajes.
  • Centro de notificaciones con estado leído/no leído (ya hay base en el MVP).
HU-61Accesibilidad WCAG 2.1 AA

Como usuario con discapacidad, quiero una interfaz accesible, para usar la plataforma sin barreras.

  • Contraste, navegación por teclado y roles ARIA correctos.
  • Auditoría automatizada (axe) integrada en CI.
HU-62Internacionalización (i18n) y documentación de API

Como usuario/integrador, quiero soporte multi-idioma y documentación de API, para ampliar el alcance y facilitar la integración.

  • i18n ES/EN en el frontend con detección de idioma.
  • Especificación OpenAPI publicada y versionado de API (/api/v1).

Sección 3 — Servidor MCP sobre el comercio electrónico

30 historias [MCP] que exponen funcionalidades de TerraShare a través de un servidor MCP (Model Context Protocol), bajo autenticación e importable desde Claude Code o Codex (vía .mcp.json). Para cada una se indica la tool que la expone, la autenticación requerida y qué le permite hacer al agente.

Modelo de autenticación del MCP: el servidor se autentica con OAuth 2.1 (token emitido por Clerk) o con API keys con alcances (scopes): read, tenant, owner y admin. Cada tool declara el scope mínimo requerido; el servidor valida identidad y permisos en cada invocación y aplica rate limiting por clave.

Catálogo y terrenos vía MCP

HU-63[MCP]Buscar terrenos

Como agente de IA, quiero buscar terrenos con filtros, para responder consultas del usuario sobre la oferta disponible.

  • Devuelve resultados paginados respetando los filtros (uso, provincia, precio…).
  • No expone terrenos en draft/inactive.
Tool: search_lands
Auth: API key scope read (público autenticado)
Permite: que el agente consulte el catálogo y resuma opciones para el usuario.
HU-64[MCP]Obtener detalle de terreno

Como agente, quiero obtener la ficha completa de un terreno, para dar información precisa.

  • Retorna ubicación, área, usos, precio y disponibilidad.
  • Devuelve error controlado si no existe.
Tool: get_land
Auth: scope read
Permite: que el agente describa un terreno concreto al usuario.
HU-65[MCP]Publicar un terreno

Como dueño (vía agente), quiero publicar un terreno desde el agente, para listar mi parcela rápidamente.

  • Valida campos requeridos antes de crear.
  • Crea el terreno en draft asociado al dueño autenticado.
Tool: create_land
Auth: scope owner (token del dueño)
Permite: que el agente cree publicaciones en nombre del dueño.
HU-66[MCP]Actualizar un terreno

Como dueño (vía agente), quiero actualizar los datos de mi terreno desde el agente, para mantenerlo al día.

  • Solo el dueño/admin puede modificar; respeta ownership.
  • No permite alterar id ni dueño.
Tool: update_land
Auth: scope owner
Permite: que el agente edite atributos del terreno.
HU-67[MCP]Cambiar estado de un terreno

Como dueño (vía agente), quiero activar/desactivar mi terreno desde el agente, para controlar su visibilidad.

  • Acepta solo estados válidos (draft/active/inactive).
  • Registra evento de auditoría.
Tool: set_land_status
Auth: scope owner
Permite: que el agente publique o retire un terreno del catálogo.
HU-68[MCP]Listar mis terrenos

Como dueño (vía agente), quiero listar mis terrenos desde el agente, para revisarlos.

  • Devuelve solo los terrenos del dueño autenticado.
  • Incluye estado y métricas básicas.
Tool: list_my_lands
Auth: scope owner
Permite: que el agente resuma el portafolio del dueño.
HU-69[MCP]Eliminar un terreno

Como dueño (vía agente), quiero eliminar un terreno desde el agente, para retirarlo.

  • Solo dueño/admin; pide confirmación explícita del agente.
  • Registra auditoría land/deleted.
Tool: delete_land
Auth: scope owner
Permite: que el agente retire publicaciones (acción destructiva, confirmada).

Solicitudes y contratos vía MCP

HU-70[MCP]Crear solicitud de alquiler

Como arrendatario (vía agente), quiero crear una solicitud de alquiler desde el agente, para reservar un terreno.

  • Valida período y uso; bloquea si el solicitante es el dueño.
  • Devuelve la solicitud creada con su estado inicial.
Tool: create_rental_request
Auth: scope tenant
Permite: que el agente inicie una reserva en nombre del arrendatario.
HU-71[MCP]Listar solicitudes

Como usuario (vía agente), quiero listar mis solicitudes desde el agente, para hacer seguimiento.

  • Devuelve solicitudes según rol (arrendatario o dueño).
  • Permite filtrar por estado.
Tool: list_rental_requests
Auth: scope tenant u owner
Permite: que el agente reporte el estado de las solicitudes.
HU-72[MCP]Gestionar estado de solicitud

Como dueño (vía agente), quiero aprobar o rechazar solicitudes desde el agente, para gestionar la demanda.

  • Aplica transiciones válidas y verifica ownership.
  • Respeta la regla de no solapamiento.
Tool: update_request_status
Auth: scope owner
Permite: que el agente apruebe/rechace reservas por el dueño.
HU-73[MCP]Generar contrato
